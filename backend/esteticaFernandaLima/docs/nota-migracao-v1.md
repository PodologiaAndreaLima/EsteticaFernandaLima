# V1 — armazenamento de notas (manual, não autoexecutável)

Pré-requisito: MySQL 8.0.16+ local e isolado, banco de teste vazio para as cinco tabelas novas, backup verificado e janela aprovada. Conferir com `SHOW CREATE TABLE usuario.usuario` e `SHOW CREATE TABLE servico_produto.servico_produto` a existência de `usuario.usuario.id BIGINT` e `servico_produto.servico_produto.id_produto_servico INT`, índices PK, tipos assinados iguais, ENGINE=InnoDB e collation compatível. Os mapeamentos legados usam `@Table(schema="usuario")` e `@Table(schema="servico_produto")`; **isso não comprova** que esses bancos/tabelas existem no MySQL instalado. Se divergirem (inclusive se existirem apenas tabelas não qualificadas no banco padrão), parar e reconciliar esquema/mapeamento antes de executar. FKs entre bancos MySQL precisam apontar para tabelas InnoDB no mesmo servidor; nunca criar bases vazias para contornar uma divergência. Nunca aplicar em produção automaticamente: `ddl-auto=update` legado pode tentar alterar as tabelas; no sandbox definir `spring.jpa.hibernate.ddl-auto=validate` somente após instalação e conferência, sem mudar configuração global nesta entrega.

Aplicação autorizada: com cliente MySQL conectado **apenas à instância local de teste**, `USE <banco_teste>; SOURCE <caminho_absoluto>/main/resources/db/migration/V1__nota_estoque.sql;` (substituir placeholders no cliente, não interpolar entradas não confiáveis). Registrar versão, data, checksum SHA-256 do arquivo, operador e resultado em registro de migração do ambiente. Conferir `SHOW CREATE TABLE` de cada tabela, constraints e índices em `information_schema`, e executar inserts sintéticos negativos em transações de teste para UNIQUE por dono/item, FKs, CHECK de quantidade e DECIMAL(19,2) (testar valor exato e rejeição por excesso; MySQL pode arredondar escala excessiva, validar escala antes do banco). MySQL DDL efetua commit implícito; falha parcial exige inventário manual antes de repetir.

Rollback **somente no sandbox e após backup**, sem notas reais e sem movimentações: `DROP TABLE nota_fiscal_identidade; DROP TABLE nota_fiscal_job; DROP TABLE movimentacao_estoque; DROP TABLE nota_fiscal_item; DROP TABLE nota_fiscal_importacao;` nessa ordem. Nunca usar esse rollback para dados reais: migração reversa deve preservar histórico, reserva e movimentos.

Contrato: upload reserva nota, job e identidade numa transação; `UNIQUE(usuario_id,tipo_identidade,identidade_digest)` serializa dedupe por dono. A identidade só é removida na mesma transação que descarta a nota; a nota permanece histórica. Late collisions viram FALHA/DUPLICADA sem id alheio. Hash hex SHA-256 de imagem e identidade, sem JSON bruto; `imagem_chave` é identificador opaco para arquivo privado fora do webroot (não URL/path público). Finalização muda status e `estado_limpeza=PENDENTE` juntos; exclusão física é acionada após o commit terminal, inclusive quando o último lease expira; exclusão bem-sucedida limpa chave e marca EXCLUIDA, falha marca FALHOU, código/instante/tentativas para retry operacional limitado pelo agendador, nunca simula exclusão. O histórico estruturado permanece. A confirmação rejeita propriedades JSON desconhecidas e valida 0.01 a 9999999.99 em decimal antes de converter custo para o Float legado; o custo exato continua no movimento. A migração não executa limpeza por si só e não comprova expurgo em ambientes não validados.
